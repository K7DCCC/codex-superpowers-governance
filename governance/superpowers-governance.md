# Superpowers 分层治理规则

> 状态：正式规则，已部署并通过新会话核心路由验证。
>
> 适用范围：Codex 中的 Superpowers 6.2.0，共 14 个子技能。
>
> 本文是用户拥有的治理事实源。插件缓存中的 `SKILL.md` 不作为治理规则的写入位置，避免插件升级覆盖本规则。

## 1. 核心原则

> 模糊请求默认走最小、可回滚的有效流程；先检查上下文，再决定是否需要澄清。
>
> 设计、计划、子代理、worktree、完整 TDD 和分支收尾属于流程升级；只有升级能显著降低返工或风险时才提出，并在调用前获得用户确认。

补充原则：

- 模糊表达不等于复杂任务。不得因为“完整处理一下”“优化一下”“帮我调整好”等口语化表达自动加载重型流程。
- 先读取相关代码、界面、测试和现有项目模式，以最小只读检查消除不确定性。
- 一个技能被调用，不代表它自动获得调用同族技能的权限。
- 用户对某个技能的一次授权，只适用于当前任务和当前流程阶段，不形成永久授权。
- 插件内部要求继续调用另一个默认禁用技能时，仍须重新经过本规则；不得自动串联。
- 已有信息足够时，`baseline-direct` 永远是正式候选。

## 2. 状态定义

### `explicit-only`

默认不自动调用。只有用户明确点名该技能或明确要求其对应机制时，才可在当前任务中调用。含糊表达不构成授权。

### `confirm-before-use`

Codex 完成最小只读检查后，只有仍存在实质性歧义且猜错会明显返工，才可说明原因并询问是否调用。用户同意前不得加载技能全文。

### `conditional-auto`

满足严格触发条件时可以自动调用，但范围必须与任务规模匹配，且不得借此继续调用其他 Superpowers 技能。

## 3. 子技能状态表

| Skill ID | 状态 | 允许触发 | 禁止自动触发 |
| --- | --- | --- | --- |
| `using-superpowers` | `explicit-only` | 用户明确要求启用 Superpowers 总入口 | 任何对话开场、普通问答、普通代码修改 |
| `writing-plans` | `explicit-only` | 用户明确要求书面实施计划 | 仅因任务有多个步骤或 `brainstorming` 已结束 |
| `executing-plans` | `explicit-only` | 用户明确要求按现有书面计划分阶段执行 | 仅因磁盘上存在计划文档 |
| `dispatching-parallel-agents` | `explicit-only` | 用户明确要求并行代理，或同意并行建议 | 仅因任务可以拆分 |
| `subagent-driven-development` | `explicit-only` | 用户明确要求用子代理执行实现 | 仅因已有计划或任务较大 |

| `systematic-debugging` | `explicit-only` | 用户明确要求使用该调试方法 | 仅因出现报错、测试失败或异常行为 |

| `verification-before-completion` | `conditional-auto` | 即将宣称任务完成、修复或通过时 | 工作尚未完成、没有可验证结果或为了触发更多流程 |

## 4. Brainstorming 需要门

只有同时满足以下条件，才可建议调用 `brainstorming`：

1. 已完成最小只读检查，包括相关文件、已有界面/行为、测试和项目惯例中的适用部分。
2. 检查后仍存在至少两个合理解释，而且它们会产生明显不同的产品行为、数据结构、接口或实现边界。
3. 直接猜测错误会导致明显返工、跨模块影响、外部副作用或难以回滚的结果。

以下情况通常不足以触发：

- 文案、颜色、间距、尺寸、局部布局或单组件视觉调整。
- 可以从截图、现有代码或同类页面中确定的交互细节。
- 遵循现有项目模式即可完成的局部行为修改。
- 小范围、可回滚、可以通过目标页面或针对性测试验证的改动。
- 用户只说了“完整”“优化”“处理好”等宽泛词语。

典型建议触发场景：

- 新产品流程存在多个会改变用户路径的合理方案。
- 涉及数据模型、公开接口、权限、认证、支付、迁移或跨模块边界，且目标不明确。
- 大范围重构会改变多个模块的职责，而现有要求不足以选择边界。

### 询问方式

询问必须包含：

- 尚未消除的关键歧义；
- 直接猜测的返工或风险；
- 不启用重型流程时可采用的最小可回滚路径。

建议措辞：

> 我检查后发现，这个需求仍有几种会影响最终结构的解释，直接选择其中一种可能造成较大返工。你希望我先继续按现有项目模式做最小可回滚修改，还是启用需求梳理流程，把目标确认清楚后再改？

同一次流程升级最多确认一次。用户拒绝后，不得换一种说法反复建议。

## 5. Verification 比例原则

`verification-before-completion` 可以条件自动调用，但验证强度必须与改动规模和风险匹配：

| 规模 | 默认验证 |
| --- | --- |
| 小型、局部、可回滚 | 检查 diff；运行最相关的目标测试或查看目标页面/行为 |
| 中型、涉及若干文件 | 相关测试、lint、类型检查或局部构建，选择能直接证明结果的组合 |
| 大型、跨模块或高风险 | 完整测试、构建和关键流程验证；涉及外部写入时另走权限门禁 |

不得为了“验证更完整”自动加载 TDD、代码审查、子代理、worktree 或分支收尾技能。

## 6. 防重复调用与权限边界

- 每个任务阶段最多有一个 Superpowers 技能处于主导状态。
- 同一个 Skill ID 在同一任务阶段不得重复加载；已加载时直接复用当前上下文。
- `brainstorming` 完成后，默认返回直接实施或等待用户指示；不得自动调用 `writing-plans`。
- `writing-plans`、`executing-plans`、子代理、worktree 和分支收尾分别需要独立、明确的用户授权。
- 安装、登录、外发、删除、修改客户端配置和改变技能可见性不因本规则获得授权。
- 无法读取治理文件、路由未命中或状态冲突时，回退到 `baseline-direct`，不自动启用 Superpowers。

## 7. 优先级

1. 系统、平台安全规则和用户当前明确指令。
2. 本治理规则与一级薄路由。
3. 单个插件 Skill 的内部流程建议。
4. 默认能力发现和模糊语义推断。

用户明确点名一个 `explicit-only` 技能，视为当前任务的调用授权；涉及安装、外发、删除、配置或其他高风险动作时，仍需单独确认。

## 8. 验收标准

- 简单 UI 或文案修改不会加载 `brainstorming`、计划、子代理、TDD 或 worktree。
- 模糊但可从项目上下文判断的小改动直接走最小可回滚路径。
- 真正存在结构性歧义时，`brainstorming` 在加载前只询问一次。
- `brainstorming` 不再自动串联 `writing-plans`。
- 任何默认禁用技能的隐式触发次数为 0。
- 完成前有新鲜验证证据，但验证范围不过度扩大。
- 任何流程升级都能说明收益、成本和回退路径。
